# The shipped 0.1.14631 build: pins and citations

`gameBuild: '14631'` is the default build (the JS `DEFAULT_GAME_BUILD`, now `dfo_core::model_blow::DEFAULT_GAME_BUILD`).
Only an explicit `'14512'` selects the vendored cut at a3eb1605; an unknown spelling normalises to the live build. A fact
readable only in the shipped build is cited `dist:<chunk>:<sha16>:<offset>@<version>`, never a line number (AGENTS.md
rule 1). Such a citation is valid only where a record under `rust/dist-pins/` lists that chunk, its sha256 and its
version; `rust/dfo-core/tests/ported_dist_pins.rs` checks every citation in the repository against those records.

These `dist:` facts are WEAK EVIDENCE (rule 1, rule 10): they are a drift finding read off a shipped, minified build,
not the vendored cut, so they can never close an assumption. They are local invariants only - the port is validated
against the JavaScript here, not against the game. The placement and default assertions live in
`rust/dfo-core/tests/gear_14631.rs` and `rust/dfo-core/tests/ported_build_default.rs`.

`rust/dist-pins/0.1.14631.json` is the pin record, copied byte for byte from `vendor/dist-pins/0.1.14631.json` while
that tree existed. The vendored record under `vendor/` and the JS test that first read it
(`test/build14631.test.js:297-316`, at the revision that still had it) are not needed by the Rust suite.

selects the vendored cut. The D4 defender set is NOT opt-in: it is simply unmodelled at both builds.

a chain reads is not traced, so this model applies no chain ratio and only the flat add; the peer's copy
(`duelGearAdd`) and the `sigilDueling()` gate are unmodelled because there is no duel state in the port. `Sy` has the
only call site (`Ob`), so the add is per blow, and each dual-wield hand is its own card and gets its own add.
